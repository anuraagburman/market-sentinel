# T-012 — Postgres portfolio and preview store

- **Implementer:** Codex   **Reviewer:** Claude Code
- **Branch:** task/T-012-postgres-store   **Depends on:** T-011 (merged `b8c5dc4`)   **Contract version:** v1 (no JSON-schema change)
- **Effort:** high for the transaction design, locking and migration. Default for wiring and tests.

## Problem
T-011 made confirm correct inside one process. Confirmed versions, receipts and previews all live in
process memory, guarded by one process-wide `IMPORT_LOCK`. A restart loses every confirmed portfolio.
A second worker has its own previews and its own lock, so stale-edit protection (`preview_revision`)
and single-winner confirm no longer hold across workers. The default store also seeds the synthetic
fixture version. Because of that, the first real confirm points `previous_version_id` at a fake
version. The async upload route also takes a threading lock on the event loop.

## User-visible outcome
With `DATABASE_URL` set, a confirmed portfolio survives a restart and every worker sees the same
previews, revisions and confirmations. The behaviour is the same as T-011: same endpoints, same status
codes, same bodies. A fresh database holds no portfolio until the user confirms one, and that first
version has `previous_version_id: null`. Developers can load the synthetic fixture into a dev database
with one explicit command.

## Configuration
- `DATABASE_URL` (already in `.env.example`), `postgresql+psycopg://…`. If it is set, the API uses the
  Postgres repositories. If it is unset, the API uses the T-011 in-memory repositories (tests and
  no-Docker dev), and the startup log says so once.
- If `DATABASE_URL` is set but the database can't be reached, or the schema isn't at Alembic `head`,
  **startup fails** with a clear message. The API never falls back to memory silently.
- `make dev` runs `alembic upgrade head` after `docker compose up` and before the API starts.
- One engine per process, created lazily, disposed in the app lifespan. Size the pool so the 12-thread
  contract test doesn't starve (pool ≥ 12, or make the test fixture's engine large enough).

## Schema (first Alembic migration, SQLAlchemy Core metadata in `app/db`, `alembic check` clean)
Every table carries `tenant_id uuid not null`. Use `numeric` **without** precision or scale for
quantities and money, so Postgres keeps the input scale. Use `timestamptz` for instants.

| Table | Key / constraints | Notes |
|---|---|---|
| `portfolio_versions` | PK `id`; `status = 'confirmed'` CHECK; `confirmed_at >= imported_at` CHECK; FK `previous_version_id → id`; **UNIQUE (`tenant_id`, `previous_version_id`) NULLS NOT DISTINCT** | The last constraint makes a forked or doubled chain impossible, even if the application logic fails. |
| `positions` | PK (`portfolio_version_id`, `instrument_id`); FK to version; `ordinal int` for row order | Row order is preserved on read via `ordinal`. `cost_basis` null stays null. |
| `import_confirmations` | PK `import_id`; **UNIQUE `idempotency_key`**; FK `portfolio_version_id`; `excluded_rows jsonb` | The T-011 `ConfirmationRecord`. The key stays globally unique until auth exists (see Excluded scope). |
| `portfolio_heads` | PK `tenant_id`; `version_id` FK | One row per tenant, locked to choose the predecessor. |
| `import_previews` | PK `id`; `revision int not null`; `document jsonb not null`; `received_at timestamptz` | The preview without `readiness`/`confirmation`, as T-011's `save` already strips them. |

- Add a `BEFORE UPDATE OR DELETE` trigger that raises on `portfolio_versions`, `positions` and
  `import_confirmations`, so confirmed data is immutable at the database level too. Test cleanup uses
  `TRUNCATE`, which these row triggers don't block.
- `downgrade()` drops everything that `upgrade()` creates.

## Round-trip fidelity (the store is not allowed to reformat anything)
`get`, `positions`, `by_import` and `by_idempotency_key` return models **equal** to what was written:
- Decimal strings keep their exact text: `"10"` stays `"10"`, `"10.50"` stays `"10.50"`, `"0.000001"` doesn't
  turn into `1E-6`.
- Timestamp strings keep their exact form: `"2026-09-25T21:00:00Z"` stays that, and
  `"2026-09-25T21:00:00.1Z"` stays that. If `timestamptz` can't reproduce the text, store the original
  string too and use `timestamptz` only for ordering and CHECKs.
- Absent and null stay different: `cash` absent stays absent (it matters for `exclude_unset`), and
  `cost_basis: null` stays null.
- Position order is the insert order.

As a result, the `201` body and a replayed `200` body are byte-identical, and so are the bodies from
before and after a restart.

## Transactions and coordination (replaces `IMPORT_LOCK`)
**`PortfolioRepository.confirm(record, version, positions)`** keeps its T-011 signature and contract.
On Postgres it is one transaction:
1. Validate in Python exactly as the in-memory store does (identity, status, timestamp order, non-empty
   positions that belong to the version, no duplicate instruments). On failure, raise `ValueError` and
   write nothing.
2. Lock the tenant head: `INSERT … ON CONFLICT DO NOTHING` the `portfolio_heads` row, then `SELECT … FOR UPDATE`.
3. Re-check `by_idempotency_key`, then `by_import`, **under that lock**. If either exists, return it and write nothing.
4. Set `previous_version_id` = the head's `version_id`, insert the version, positions and receipt,
   update the head, and commit.
5. A unique violation on `import_id` or `idempotency_key` (for example a key used by another tenant
   later) rolls back, then re-reads and returns the existing receipt. Any other database error rolls
   back and is raised.

**Previews and confirm share one per-import transaction.** Add a small unit of work to the service
layer (pick the names). For example, `with store.import_transaction(import_id) as tx:` exposes
`tx.preview` (or `None`), `tx.save(preview)` and `tx.confirm(record, version, positions)`.
- Postgres: one connection and one transaction. The first statement is
  `SELECT … FROM import_previews WHERE id = :id FOR UPDATE`. Every resolution and exclusion
  PUT/DELETE, and every confirm, runs inside it. So edits and confirm for one import are serialized
  across all workers, and confirm's `preview_revision` check, readiness check, clock read and portfolio
  insert all happen in that transaction.
- Lock order is always **preview row → tenant head**. The standalone `confirm` takes only the tenant
  head. Edits take only the preview row. That ordering rules out deadlocks.
- Reads (`GET /imports/{id}`) and upload don't take the row lock. Upload is a plain insert.
- In-memory: the same interface with a per-import lock plus the existing portfolio lock. No module-level
  lock is left. `IMPORT_LOCK` is deleted.
- `upload_import` stays `async` to read the file, then does parsing and storage off the event loop
  (`run_in_threadpool`, or move that work into a sync helper the route awaits). A threading lock or a
  blocking DB call never runs on the loop.
- Use READ COMMITTED with explicit row locks. If a serialization failure or deadlock happens anyway,
  retry the whole transaction at most 3 times, then return `503 store_unavailable`.

## Seeding
- Postgres is **never** seeded by the app or by the migration. On a fresh database,
  `GET /portfolio-versions/…0100` → `404`, and the first confirm gets `previous_version_id: null`.
- `python -m app.db.seed_fixture` (also `make seed-dev`) inserts the synthetic fixture version and
  positions through `PortfolioRepository`'s insert path (with no receipt). It is idempotent: running it
  twice is a no-op. It refuses to run unless `MS_ENV` is `dev` or `test`.
- The in-memory default stays seeded with the fixture, as in T-011, so no-DB dev and the existing
  valuation tests keep working.

## Error states
- Database unreachable or a transaction fails mid-request → `503 store_unavailable` (`{code, message}`),
  nothing written. Add 503 to the OpenAPI `responses` of the routes that write or read the store.
- Schema not at head, or `DATABASE_URL` set but unreachable at startup → the process exits non-zero.
- Missing data is never turned into a default. An unknown preview is still `404 import_not_found`,
  never an empty preview.

## Review nits folded in (from the T-011 review)
- `confirm_import` no longer computes `previous`. `build_portfolio` leaves `previous_version_id` for the
  store to set (pass `None`, or remove the parameter). The store is the only source of the predecessor.
- `FilePortfolioRepository._version` is no longer read from outside the class. Add a public accessor
  (for example `version` / `fixture_version()`) and use it in the in-memory seed, the dev seed and the
  tests.
- `test_edit_cannot_cross_confirmation_transaction` must **force** the race. Use an injected clock
  that blocks on a `threading.Event` while confirm is inside its transaction. Start an edit, assert it
  hasn't finished, release the event, and assert that the edit gets `409 import_confirmed` and the
  stored revision is unchanged. Run it on both stores.
- Out of scope here, routed to the web lane: grouping `row_has_errors` + `row_unresolved` per row in the UI.

## Tests
**Running Postgres tests.**
- Tests marked `postgres` use `TEST_DATABASE_URL`. `conftest.py` refuses any database whose name
  doesn't end in `_test`, so it can never truncate dev data. It creates the database if it's missing,
  runs `alembic upgrade head` once per session, and runs `TRUNCATE … CASCADE` on all tables before
  each test. No rollback-wrapping, because the concurrency tests need real commits.
- Without `TEST_DATABASE_URL`, the tests skip with a visible reason. **With `CI=true` and no URL,
  collection fails**, so CI can't go green by skipping.
- CI: add a `postgres:17.4-alpine` service (same image as `compose.yaml`) with a health check, and set
  `TEST_DATABASE_URL=postgresql+psycopg://sentinel@localhost:5432/sentinel_test`. `make test` then runs
  everything.
- Locally: `docker compose up -d --wait postgres`, then `TEST_DATABASE_URL=… make test`.
  Document this in `README.md`. Its test section currently says tests need no Docker; update that line.
- The Postgres tests use only that local database, with no network beyond localhost. Every other test
  stays as it is.

**Acceptance.**
1. **Repository contract.** `test_confirm_repository.py` is parametrized over `["memory", "postgres"]`, and
   every existing test passes on both unchanged, including the 12-thread single winner, the atomic
   `latest` chain, failed-transaction-writes-nothing and fractional timestamps.
   Add a preview-repository contract suite on both stores: save/get round-trip equality, copies isolate
   callers, unknown id → `None`.
2. **Round-trip fidelity.** On Postgres, the cases in "Round-trip fidelity" hold, compared by model
   equality and by JSON bytes.
3. **API on both stores.** Parametrize the T-011 confirm API suite over the stores, at minimum the
   fixture walk-through (steps 1–5, including the valuation numbers), the idempotency replay
   byte-identity, the N-thread different-key concurrency, `409 preview_changed` and post-confirm
   `409 import_confirmed`.
4. **Across workers.** Use two independent engines and app instances on one test database, standing in
   for two workers:
   - A preview uploaded on A is readable and editable on B.
   - A confirms with a revision that B has since advanced → `409 preview_changed`.
   - A and B confirm the same import concurrently with different keys → one `201`, one
     `409 import_already_confirmed`, one version in the database.
   - Two different imports for the same tenant confirmed concurrently on A and B → a linear chain. One
     version has `previous_version_id` = the other's id, and the unique constraint was never violated.
5. **Durability.** Confirm, dispose the engine, build a fresh app and engine. Then `GET /imports/{id}`
   shows `confirmation`, `GET /portfolio-versions/{id}` returns the identical body, valuation works,
   and a replayed confirm returns `200` with the identical body.
6. **Forced edit-vs-confirm race** (above) passes on both stores, 8 runs in a row.
7. **Database-level immutability.** A raw SQL `UPDATE` or `DELETE` on each of the three immutable
   tables raises. Inserting a second version with the same (`tenant_id`, `previous_version_id`) raises.
8. **No seeding.** On a fresh migrated database, the fixture id → `404`, and the first confirm has
   `previous_version_id: null`. `seed_fixture` run twice → one version. With `MS_ENV=prod` it refuses
   with a non-zero exit.
9. **Migrations.** `alembic upgrade head` on an empty database → `downgrade base` leaves no
   application tables → `upgrade head` again succeeds. `alembic check` reports no drift between the
   metadata and the migration.
10. **Startup.** With `DATABASE_URL` pointing at a database below head, or at a closed port, app
    startup raises. A store failure injected into a write route → `503 store_unavailable` and no rows
    written.
11. `grep -rn IMPORT_LOCK apps/api` → nothing.
