# T-011 — Import confirm → immutable PortfolioVersion

- **Implementer:** Codex   **Reviewer:** Claude Code
- **Branch:** task/T-011-import-confirm   **Depends on:** T-004, T-005, T-006 (merged)   **Contract version:** v1
- **Effort:** default (high for the confirm rules and idempotency in `domain/confirm.py` and the store)

## Problem
A user can upload a CSV, see row issues, and pick instruments, but nothing turns that preview into
the portfolio every later number depends on. Valuation still reads a hand-written fixture version.
The confirm step is where silent damage would get locked in: an accidental duplicate becomes a
doubled position, an unresolved symbol becomes a guess, a retried request becomes two versions, or a
confirmed version gets edited later.

## User-visible outcome
Once every remaining row is resolved and error-free, the user excludes the rows they don't want (for
example the duplicate row 20) and confirms. The API creates one immutable confirmed `PortfolioVersion`
plus its positions, and valuation works on it immediately. The preview shows whether confirm is
possible and, if not, which rows block it and why. A retried confirm returns the same version. A
confirmed import can no longer be edited.

## Row decisions (preview, before confirm)
Add row exclusion next to the existing resolution routes:
- `PUT /imports/{id}/rows/{row_number}/exclusion` → `200` row, now `excluded: true`
- `DELETE /imports/{id}/rows/{row_number}/exclusion` → `200` row, `excluded: false`

Any row can be excluded. Exclusion never changes `raw`, `parsed`, `issues` or `resolution`; excluding
one of two duplicates doesn't merge them. Blank rows (`blank_row`) are always treated as excluded, with
reason `blank_row`, and can't be un-excluded (`409 row_not_includable`).

The preview model gains:
- `revision: int`, starting at `0`. It goes up by 1 on every successful resolution PUT/DELETE and
  exclusion PUT/DELETE, **including no-op repeats** (simple and predictable).
- per row `excluded: bool`
- `confirmation: {portfolio_version_id, confirmed_at} | null`
- `readiness: {confirmable: bool, blockers: [{row_number | null, code, message}]}`, computed on every
  read from the current rows (never stored), in the order: row order, then file-level blockers.

After confirm, every row-decision route returns `409 import_confirmed`.

## Confirm rules (in `domain/confirm.py`, pure: no I/O, no clock)
Among included rows (not excluded), each of these is a blocker:

| Code | Rule |
|---|---|
| `row_has_errors` | row `status == "error"` |
| `row_unresolved` | `resolution.status` ≠ `resolved` (covers `ambiguous`, `unresolved`, `not_attempted`) |
| `instrument_missing` | resolved `instrument_id` no longer in the instrument repository |
| `duplicate_instrument` | two or more included rows resolve to the same `instrument_id`. Every such row is listed. Duplicates never aggregate (product.md, account/lot semantics come later). |
| `no_included_rows` | file-level, `row_number: null`: nothing left to confirm |

Warnings (`missing_cost_basis`, `currency_mismatch`, `duplicate_row` whose twin is excluded, and so on)
don't block. **Confirm does not re-resolve.** It uses the stored resolutions the user reviewed
(this settles the T-005 open question). A row resolved on its preview date stays that instrument.

Mapping, one position per included row, in row order:
`instrument_id` and `display_symbol` from the resolution; `quantity`, `cost_basis` (null stays null) and
`currency` copied from `parsed` exactly as parsed (no re-formatting, no conversion). A non-USD row is
allowed. Valuation already reports it as `currency_out_of_scope`. No `account_label`.

Version: `id` new UUID; `tenant_id` = a single documented placeholder constant
`00000000-0000-4000-8000-000000000101` (the fixture tenant) until auth exists; `base_currency: "USD"`
(ADR-002 §4); `imported_at` = preview `received_at`; `source_hash` = `"sha256:" + file_sha256`;
`status: "confirmed"`; `confirmed_at` = injected clock, UTC `Z`, and never earlier than `imported_at`
(else `ValueError`, since that means the clock is broken); `previous_version_id` = that tenant's latest
confirmed version at confirm time, or `null`; `cash` absent (the CSV carries none; absent means unknown).

## Endpoints
**`POST /imports/{id}/confirm`**. Header `Idempotency-Key` (1–200 printable ASCII) is required.
Body `{"preview_revision": int}`, the revision the user reviewed.
- `201` → `{portfolio_version, positions[], import_id, excluded_rows: [{row_number, reason}]}`.
  `reason` is `user_excluded` or `blank_row`.
- Same key, same import, same body, already confirmed → `200` with the **identical** body.
- Missing/invalid key → `400 idempotency_key_required`. Same key reused with a different import or body →
  `422 idempotency_key_reused`.
- Unknown import → `404 import_not_found`. `preview_revision` ≠ current → `409 preview_changed`.
  Blockers present → `409 import_not_confirmable`, with the `blockers` list in the problem body.
  Already confirmed under a different key → `409 import_already_confirmed`, with `portfolio_version_id`.

**`GET /portfolio-versions/{id}`** → `200 {portfolio_version, positions[]}`. Unknown → `404 portfolio_version_not_found`.

`GET /portfolio-versions/{id}/valuation` stays unchanged and reads from the same store.

Problem bodies stay `{code, message}`, plus `blockers` or `portfolio_version_id` where noted above.
Make those optional fields on the existing `Problem` model, or add a subclass. Either way, OpenAPI
has to show them.

## Store
Extend `PortfolioRepository` with `confirm(record, version, positions) -> ConfirmationRecord`,
`by_import(import_id)`, `by_idempotency_key(key)` and `latest(tenant_id)`. `ConfirmationRecord` =
`{import_id, idempotency_key, request_fingerprint, portfolio_version_id, excluded_rows}` is internal,
not a contract.
- `confirm` is **atomic and single-winner**. It validates everything first, then writes the version,
  positions and record together under one lock, or nothing. If the import already has a record, it
  writes nothing and returns the existing record, and the service maps that to 200/409 as above.
- No update or delete methods. Reads return frozen models or copies, so callers can't mutate stored state.
- The confirmation lives in the portfolio store, not the preview store. The preview's `confirmation`
  field and the post-confirm 409s read it from there, so there is exactly one source of truth.
- Default implementation: `InMemoryPortfolioRepository`, process-local, documented as temporary until
  T-012, and **seeded with the validated fixture version** from the existing file loader. That keeps
  T-006 valuation of `…0100` working. Tests inject an empty one.
- `ObservationRepository` is unchanged.

The T-012 Postgres repository must pass the same repository contract tests. Write them as a reusable
suite parametrized over implementations, with only the in-memory one for now.

## Invariants
- A confirmed version and its positions never change. Corrections are a new import and a new version
  with `previous_version_id`.
- One import → at most one version, whatever retries or concurrent requests happen.
- Nothing becomes zero, a guess, or an aggregate. Excluded and blank rows are listed in the response,
  never dropped silently.
- `Decimal`/strings only, never `float`. Timestamps UTC `Z`. The clock is injected (the existing `get_clock`).
- Tests make no network or database calls.

## Acceptance
**Fixture walk-through** (clock `2026-09-25T20:30:00Z` at upload, `2026-09-25T21:00:00Z` at confirm,
empty injected store):
1. `POST /imports` with `holdings.csv` → `revision 0`, `confirmable: false`. Blockers: row 1
   `duplicate_instrument`, row 2 `row_unresolved`, row 5 `row_unresolved`, row 20 `duplicate_instrument`
   (and nothing else).
2. Confirm now → `409 import_not_confirmable` with those same blockers.
3. PUT resolution row 2 → Synthela 02 (`…0002`); PUT resolution row 5 → Synthela 05 (`…0005`);
   PUT exclusion row 20 → `revision 3`, `confirmable: true`.
4. Confirm with `preview_revision: 3` → `201`: 19 positions whose `(instrument_id, display_symbol,
   quantity, cost_basis, currency)` equal `positions.json` in order. `source_hash` equals the fixture's
   `sha256:5d37…ee9c`. `imported_at`/`confirmed_at` match the fixture version. `previous_version_id`
   is `null`. `cash` is absent. `excluded_rows: [{row_number: 20, reason: "user_excluded"}]`.
5. `GET /portfolio-versions/{new id}/valuation?cutoff=2026-09-25T21:00:00Z` reproduces the T-006
   acceptance numbers (`priced_value 12812.83`, coverage 19/18/1, SYN01 weight `0.488183`, …).
   Asserting the full body equal to the fixture version's valuation, apart from the id, is enough.

**Rules and edges** (injected, built in tests):
- Idempotency: the same key and body retried → `200` with a byte-identical body, and the store holds
  one version. The same key on another import or with another `preview_revision` → `422`. A new key
  after confirm → `409 import_already_confirmed`.
- Concurrency: N threads confirm the same import with different keys → exactly one `201`, and the rest
  get `409 import_already_confirmed` for that same version.
- `409 preview_changed` when the revision is stale. After confirm, every resolution/exclusion route →
  `409 import_confirmed`.
- Excluding both rows 1 and 20 (after the step-3 fixes) → confirmable; 18 positions, none for SYN01.
  Excluding every row → only `no_included_rows`.
- A blank row is auto-excluded (`reason: blank_row`) and can't be un-excluded. An error row blocks
  until it's excluded. A `currency_mismatch` warning or a CAD row confirms, and valuation reports
  `currency_out_of_scope`.
- Two different rows (different quantities) resolved to the same instrument → both `duplicate_instrument`.
- An instrument removed from an injected instrument repository after resolution → `instrument_missing`.
- Confirm never re-resolves: swap in an instrument repository whose mapping for the row's symbol changed
  after preview, and the confirmed `instrument_id` is still the reviewed one.
- A second confirmed import for the same tenant → `previous_version_id` = the first version's id.
- Immutability: mutating any object returned by the store, or by a response model, and then re-reading
  gives the original. The repository has no update/delete.
- Properties: excluding and then un-excluding a row leaves `readiness` as it was (with a higher
  revision). Permuting which duplicate is excluded changes only which row number appears in
  `excluded_rows` and the position's source row, never the position values.
